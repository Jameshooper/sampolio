# Projections & Reconciliation — deep reference

How Sampolio computes every number: the three projection engines, the reconciliation
(anchoring) system that keeps them honest, and everything that feeds them. This is the
deep companion to the summaries in the root `AGENTS.md` and the per-page `AGENTS.md`
files. Related docs: [bank-sync.md](bank-sync.md) (where synced balances/transactions
come from), [mortgage.md](mortgage.md) (the mortgage amortization engine whose output is
injected here), [features.md](features.md) (budgets/split, whose outputs also fold in),
[architecture.md](architecture.md) (server actions, caching, storage).

## 1. Overview

Three pure engines compute numbers; server actions gather their inputs:

| Engine | File | Output | Direction |
|---|---|---|---|
| Cashflow projection | `src/lib/projection.ts` → `calculateProjection` | `MonthlyProjection[]` per cash account | forward from the anchor |
| Retrospective | `src/lib/retrospective.ts` → `calculateRetrospective` | `MonthlyProjection[]` (`isActual: true`) | backward from the anchor, real bank data only |
| Wealth projection | `src/lib/wealth-projection.ts` → `calculateWealthProjection` | `WealthProjectionMonth[]` (net worth) | forward, all entity types |

All three are pure functions (no I/O). `getProjection` in `src/lib/actions/projection.ts`
assembles the cashflow + retrospective inputs server-side; the wealth projection is
assembled **client-side** on `/overview` (`src/app/(dashboard)/overview/page.tsx`), which
fetches entities, per-entity latest snapshots, per-account cash projections, mortgage
inputs, card liabilities (`getCardLiabilities` in `src/lib/actions/bank.ts`) and the
split net balance (`getMySplitNetBalance`), then runs `calculateWealthProjection` in the
browser.

**Reconciliation is the anchoring backbone.** Every engine re-bases on the latest
`BalanceSnapshot` per entity via `resolveAnchor` (`src/lib/projection.ts`), so a monthly
check-in — or a bank sync — moves every forecast to reality without editing any entity's
genesis data.

## 2. Cashflow projection (`calculateProjection`)

```ts
calculateProjection(
  account: FinancialAccount,
  recurringItems: RecurringItem[],
  plannedItems: PlannedItem[],
  taxedIncomes: TaxedIncome[] = [],
  filters?: ProjectionFilters,
  latestSnapshot?: BalanceSnapshot | null,
  mortgageTransfers: MortgageTransfer[] = [],
  budgetTransfers: BudgetTransfer[] = [],
  cardBillTransfers: CardBillTransfer[] = [],
  currentMonthActuals?: CurrentMonthActuals | null,
  goalTransfers: GoalTransfer[] = [],
  tripTransfers: TripTransfer[] = []
): MonthlyProjection[]
```

- **Month list** (`generateMonthList`): starts at the anchor month; ends at
  `account.customEndDate` if set, else `anchor + planningHorizonMonths − 1` — a rolling
  horizon measured from the anchor, so the forward window never shrinks between
  check-ins.
- **Running balance**: starts at `anchor.startBalance`; each month's
  `endingBalance = startingBalance + totalIncome − totalExpenses` chains into the next.

### Per-month item expansion

- **Recurring items** — `isRecurringItemActiveInMonth`: must be `isActive`, within
  `startDate..endDate`, and on an occurrence month: `getIntervalMonths` maps frequency to
  months (`monthly`=1, `quarterly`=3, `yearly`=12, `custom`=`customIntervalMonths`) and
  the item fires when `monthsBetween(startDate, month) % interval === 0`.
- **One-off planned items** (`kind: 'one-off'`): fire in their `scheduledDate` month.
- **Repeating planned items** (`kind: 'repeating'`): occurrences generated by
  `getPlannedRepeatingOccurrences` from `firstOccurrence` at the frequency interval,
  bounded by the item's `endDate` and the projection window.
- **Shared items**: any of the above with `isShared` contributes
  `amount × (shareRatio ?? 0.5)`.
- **Reimbursements**: a one-off with `isReimbursable`, `reimbursementStatus: 'pending'`
  and `expectedReimbursementMonth` additionally emits an income line
  `Reimbursement: {name}` (category `Reimbursement`) in that month, using the
  share-adjusted amount.
- **Taxed income**: contributes **`netAmount`** (never `grossAmount`), `source:
  'taxed-income'`. One-off fires on `scheduledDate`; recurring uses
  `startDate`/`frequency`/`customIntervalMonths`/`endDate` with the same interval logic
  and skips any month listed in `skippedOccurrences` (one-offs ignore the field);
  must be `isActive`. The stored net is **frozen at write time**
  (`calculateTaxedIncomeNet`, `src/lib/taxed-income-utils.ts` — taxes the raw gross,
  unlike `calculateNetSalary`'s benefit-inclusive base); when a row has
  `useSalaryTaxSettings`, the salary actions cascade-recompute it on every salary
  config create/update/delete (`recomputeSalaryLinkedTaxedIncomes` in
  `src/lib/db/taxed-income.ts`, invalidating
  `user:{id}:account:{accountId}:taxed-income` only when numbers changed).
  `getProjection` returns the full `taxedIncomes` alongside `salaryConfigs` so the
  cashflow page can synthesize the gross→Tax/Contributions/Other-deduction Sankey
  flows for these lines, mirroring salary.

### Salary

There is no salary path inside the engine. A `SalaryConfig` stores a computed
`netSalary` (from `calculateNetSalary` in `src/lib/salary-utils.ts`: taxable benefits
increase the tax/contributions base but are not received as cash; net = gross − tax −
contributions − otherDeductions). When `isLinkedToRecurring`, the DB layer
(`src/lib/db/salary-configs.ts`) creates/updates a plain monthly recurring **income**
item `Salary: {name}` with `amount = netSalary` — the projection sees it as an ordinary
`source: 'recurring'` line. The `'salary'` member of the `ProjectionLineItem['source']`
union is never emitted by `calculateProjection`; `getProjection` returns `salaryConfigs`
alongside the projection purely for UI display.

### Filters (`ProjectionFilters`)

`startDate` skips months before it, `endDate` breaks the loop after it; `categories`,
`itemTypes` (`income`/`expense`) and `itemKinds` (`recurring`/`one-off`/`repeating`)
filter individual lines. Two subtleties:

- `filters.startDate` skips whole months **before applying their flows** — the first
  rendered month starts at the raw anchor balance, so balances under a start filter are
  not the same as the unfiltered projection's balances for those months.
- Injected transfer lines (mortgage/budget/card) are **not** subject to
  category/type/kind filters; only real items are.

### Output shape

`MonthlyProjection` (`src/types/index.ts`): `yearMonth`, `year`, `month`,
`startingBalance`, `totalIncome`, `totalExpenses`, `netChange`, `endingBalance`,
`incomeBreakdown`/`expenseBreakdown` (`ProjectionLineItem[]`), optional `isActual`
(retrospective months only). `ProjectionLineItem`: `itemId`, `name`, `amount` (always
positive), `category?`, `source` (union: `recurring | planned-one-off |
planned-repeating | salary | taxed-income | mortgage-payment | budget | credit-card |
bank-actual | goal | trip`), `isOverridden?`.

`calculateYearlyRollups` groups monthly rows into `YearlyRollup` per calendar year
(summed income/expenses, first month's `startingBalance`, last month's `endingBalance`,
plus the constituent `months`).

## 3. Anchoring (`resolveAnchor`)

```ts
resolveAnchor(genesisMonth, genesisBalance, latestSnapshot?, negate = false): ProjectionAnchor
// → { startMonth, startBalance }
```

If a snapshot exists **at or after** the genesis month, the projection re-bases on
`{ snapshot.yearMonth, snapshot.actualBalance }`; otherwise it falls back to genesis.
"Latest" snapshot means greatest `yearMonth` for that `(entityType, entityId)`
(`getLatestSnapshot` in `src/lib/db/reconciliation.ts` sorts by `yearMonth`), not the
most recent write. `negate: true` converts a debt snapshot's stored-negative balance back
to positive principal.

Genesis per entity type: cash account `startingDate`/`startingBalance`; investment
`valuationDate`/`startingValuation`; receivable `startDate`/`initialPrincipal`; debt
`startDate`/`initialPrincipal` (with `negate`).

Consequences:

- A monthly check-in moves the anchor forward and re-bases every balance on the
  confirmed value; **the account's start month never needs editing** — the anchor
  supersedes genesis whenever a snapshot exists.
- The planning horizon is measured from the anchor (rolling window), so forecasts keep a
  constant forward depth.
- Bank sync writes anchor snapshots too (§9), so a linked account re-anchors to its real
  balance automatically.
- Elapsed months behind the anchor simply fall out of the forecast (and, for a
  bank-linked account, are replaced by the retrospective, §6).

## 4. Occurrence overrides

A single month of a recurring item is overridden by a one-off `PlannedItem` carrying
`isRecurringOverride: true`, `linkedRecurringItemId`, `scheduledDate` (the overridden
month) and optional `skipOccurrence`. Written by
`upsertRecurringItemOccurrenceOverride` (`src/lib/actions/planned.ts`), which updates
the existing override for that item+month or creates a new one seeded from the recurring
item's values. The DB layer (`src/lib/db/planned-items.ts`) persists all three flags —
dropping them on a write path re-introduces double counting.

In `calculateProjection`, override items are **removed from regular planned-item
processing** and indexed as `recurringItemId → month → PlannedItem`. When the recurring
item fires in an overridden month:

- `skipOccurrence: true` → the occurrence is skipped entirely;
- otherwise the line uses the override's `name`/`amount`/`category` (falling back to the
  recurring item's), keeps the recurring item's `type` (an override cannot flip
  income↔expense), and is flagged `isOverridden: true`.

The override is therefore applied **in place of** that month's occurrence, never in
addition to it.

**Expiry**: the engine ignores overrides with `scheduledDate` earlier than
`projectionStart − 2 months`. `cleanupExpiredOverrides` deletes them from disk using the
same window computed from the **anchor** (`anchor.startMonth − 2`), which guarantees it
only deletes overrides the projection already ignores — forecasts never change. It
auto-runs (fire-and-forget) after every override upsert/delete.

## 5. Injected read-only lines (the transfer pattern)

`getProjection` (`src/lib/actions/projection.ts`) computes five transfer arrays in
parallel (`gatherProjectionInputs` in `src/lib/projection-inputs.ts` gathers
`mortgageTransfers`/`budgetTransfers`/`goalTransfers`/`tripTransfers`;
`computeCardBillTransfersForAccount` is called separately, see §5) and passes them as
positional args to `calculateProjection`: `mortgageTransfers`, `budgetTransfers`,
`cardBillTransfers`, then (after `currentMonthActuals`) `goalTransfers`, `tripTransfers`
— appended at the end so existing positional call sites (e.g. `src/lib/bank/sync.ts`)
compile unchanged. Each array is grouped per month inside the engine and emitted as
read-only lines; amounts ≤ 0.005 are dropped. Every gatherer is wrapped in try/catch — a
mortgage/budget/card/goal/bank failure logs and returns `[]`, never breaking the core
projection.

| Transfer | Helper | Line | Deep link (cashflow `handleEditItem`) |
|---|---|---|---|
| `MortgageTransfer` | `getMortgageTransfersForAccount` | `Mortgage: {name}`, category `Housing`, `source: 'mortgage-payment'`, `itemId` = mortgageId | `/mortgage` |
| `BudgetTransfer` | `getBudgetTransfersForAccount` | `Budget: {name}` (expense) / `Budget: {name} (funding)` (income), `source: 'budget'`, `itemId` = budgetId | `/budgets/{id}` |
| `CardBillTransfer` | `getCardBillTransfersForAccount` | `Card: {name}` (+ ` (estimate)`), category `Credit cards`, `source: 'credit-card'`, `itemId` = bank-link id | `/bank` |
| `GoalTransfer` | `getGoalTransfersForAccount` | `Goal: {name}` (expense), category `Goals`, `source: 'goal'`, `itemId` = goalId | `/goals` |
| `TripTransfer` | `getTripTransfersForAccount` | `Per diem: {name}` (income), `source: 'trip'`, `itemId` = tripId | `/budgets#trips` |

- **Mortgage**: for each non-archived shared mortgage whose member record for this user
  has `linkedAccountId === accountId`, the full amortization engine runs
  (`calculateMortgageProjection`, horizon = genesis + longest term + 24 months) and the
  member's per-month `monthlyDeposit` becomes the transfer. It tracks rate resets and
  reconciled actuals automatically. See [mortgage.md](mortgage.md).
- **Budget**: budgets with `status === 'confirmed' && !isArchived && linkedAccountId ===
  accountId` run through `computeBudgetTransfers` (`src/lib/budget-utils.ts`): per budget
  month, aggregate planned costs → one expense line, allocated usable funding → one
  income line, both multiplied by `budget.exchangeRate ?? 1` (so amounts arrive in the
  account's currency). Before that, each budget's funding sources are passed through
  `hydrateBudgetFundingFromTrips(budget, trips)` so a trip-linked per-diem source
  (`linkedTripId`) contributes the trip's **live** per-diem total (the stored amount is a
  write-time snapshot; a deleted trip leaves the snapshot standing) — see
  [features.md](features.md) §Budgets.
- **Card bills**: for each bank link with `accountRole === 'credit-card'`,
  `!isExcluded`, and `linkedFinancialAccountId === accountId`:
  - **Real bills** from `computeCardBilling` (`src/lib/bank/card-billing.ts`, pure): the
    firm bill for the most recent closed statement (balance =
    `lastStatementBalance` if known, else net cycle spend), due on the next
    `paymentDueDay` after close (`basis: 'statement'`); plus the **previous** closed
    statement's bill (from its `cycleSpend` only — `lastStatementBalance` never applies to
    it) while its due month is still current-or-future, so the current month's already-due
    bill doesn't disappear mid-month when `now` crosses the statement day.
  - **The open cycle's bill** (`basis: 'open-cycle'`, emitted when cycle config exists
    and the computed amount exceeds €0.005): actual booked+pending spend so far + the cycle forecast
    (`taggedSpendForMonth` for the cycle's spend month + `expectedMonthlySpend`)
    pro-rated over the fraction of the cycle still ahead — real transactions drive the
    number and the flat estimate only fills the not-yet-elapsed remainder. Labeled
    "(cycle in progress)" in the cashflow line.
  - **Forecast bills** (`basis: 'forecast'`) for every due month after that, up to
    `currentMonth + max(planningHorizonMonths ?? 120, 1)`: amount =
    `taggedSpendForMonth` (expenses tagged with this card, see below) for the cycle's
    spend month (`due − 1` month when `paymentDueDay <= statementDay`, else `due`) + the
    card's `expectedMonthlySpend` buffer; always `isEstimate: true`, labeled "(estimate)".

**`paidByCardLinkId` exclusion**: before calling `calculateProjection`, `getProjection`
filters out every recurring/planned item whose `paidByCardLinkId` is set — those
expenses do not hit cash directly; they surface only inside the card's forecast bill
(via `taggedSpendForMonth`). Category extraction (`getUniqueCategories`) still sees the
unfiltered lists.

- **Goals**: a goal injects only when `goalInjectsIntoCashflow(goal)`
  (`src/lib/goal-utils.ts`) is true — the single predicate, shared by
  `getGoalTransfersForAccount` and the goal-plan engine — requiring
  `goalType === 'spend'`, `injectIntoCashflow: true`, a `targetDate`,
  `trackingMethod === 'account-balance'`, a `linkedAccountId`, and not archived. One
  transfer per qualifying goal, at its `targetDate`, `amount = targetAmount`. See
  [features.md](features.md) §Goals for the joint funding-plan engine
  (`computeGoalPlan`) that reasons about these claims across competing goals.
- **Trips**: `getTripTransfersForAccount` (`src/lib/projection-inputs.ts`) emits one
  transfer per trip whose `status !== 'reimbursed'` and `linkedAccountId === accountId`,
  at `expectedReimbursementMonth`, `amount = calculatePerDiem(trip).total` (the pure
  Vero.fi per-diem engine, `src/lib/per-diem-utils.ts`, run against the trip's
  snapshotted `TripRateSnapshot` — see [features.md](features.md) §Trips). Marking a
  trip `'reimbursed'` stops the injection, same as a settled budget/goal. It is **also**
  suppressed for any trip whose per-diem already reaches cashflow through an active
  budget: `tripIdsFundedByActiveBudgets(budgets)` (`src/lib/budget-utils.ts`; confirmed,
  not archived, account-linked, with a per-diem funding source carrying `linkedTripId`)
  is subtracted so the budget's funding-income line and the trip's own income line don't
  double-count (a draft/archived budget doesn't suppress it — the money isn't reaching
  cashflow yet). See [features.md](features.md) §Budgets → "Trip-funded per-diem sources".

## 6. Retrospective (bank-actual past months)

Separate from the forecast, `getProjection` returns `retrospective:
MonthlyProjection[]` — past months rebuilt **purely from real booked bank
transactions**, no Sampolio forecast items.

**Gathering** (`getRetrospectiveForAccount`, `src/lib/actions/projection.ts`): collects
all bank links with `accountRole` `'cash'` or `'savings'`,
`linkedFinancialAccountId === accountId`, `!isExcluded`; flattens their transaction
ledgers; resolves the same anchor as the forecast; calls `calculateRetrospective`.
Returns `[]` when no such link exists or there are no transactions, so non-bank accounts
are untouched.

**Engine** (`calculateRetrospective`, `src/lib/retrospective.ts`):

- `RETROSPECTIVE_MONTHS_BACK = 24` — the cap on months reconstructed (matches the
  ~24-month bank backfill window; the practical limiter is how much history was
  backfilled — see [bank-sync.md](bank-sync.md)).
- **Booked only**: `tx.status !== 'booked'` is skipped (pending may still change).
  Months at/after `anchor.startMonth` are ignored — that is the forecast's territory.
- **Grouping** (`groupKeyFor`): counterparty name → first line of `remittanceInfo` →
  `bankTransactionCode` → `'Other'`. Credits (`amount > 0`) become income groups, debits
  expense groups, both with positive magnitudes; the group's `category` hint is the
  first non-empty `bankTransactionCode`. Line `itemId` is the deterministic
  `bank-actual:{accountId}:{yearMonth}:{kind}:{name}`; `source: 'bank-actual'`.
- **Card-payment collapse** (optional `cardPayments` input, gathered by
  `getCardPaymentSourcesForAccount` in `projection-inputs.ts`): a debit matching one of
  the account's cards' settlement credits — exact cents, booking dates within ±4 days
  (`matchCardPayments`, `src/lib/bank/card-payment-match.ts`, pure/greedy/one-to-one) —
  is pulled out of counterparty grouping and aggregated into one expense line per card:
  `itemId` = the card **link id**, name `Card: {cardName}`, category `'Credit cards'`,
  `source: 'credit-card'`. Month totals are conserved. The link-id `itemId` is what
  keys the cashflow page's per-month `cardBreakdowns` map, so the Sankey/treemap expand
  the line into the card's purchases (the breakdown action's past-month fallback slices
  the settled cycle — see [bank-sync.md](bank-sync.md) §10). Omitting `cardPayments`
  yields the plain grouping.
- **Backward balance chaining**: walking from the month just before the anchor, each
  month's `endingBalance` equals the next month's `startingBalance`, seeded with
  `anchor.startBalance` — so the newest past month meets the forecast's first month
  exactly.
- **Contiguity**: a month with zero transactions stops the walk (keeps the balance chain
  continuous). The walk is **not** bounded by the account's Sampolio `startingDate` —
  real bank history is valid regardless of when the account was created here.
- Every row carries `isActual: true`; rows are returned oldest→newest.

**UI** (`src/app/(dashboard)/cashflow/page.tsx`): actual months render to the left of
the forecast; clicking a `bank-actual` line deep-links to `/bank`; the Add Income / Add
Expense buttons are disabled on actual months ("Past months show real bank data and
cannot be edited").

## 7. Current-month actualization (`applyCurrentMonthActuals`)

For a bank-linked cash account, the anchor balance for the current calendar month is the
**LIVE synced balance** — it already reflects everything paid or received so far. Running
the full monthly forecast on top of that anchor would double-count whatever has already
cleared. `calculateProjection` fixes this only for the month where `yearMonth ===
anchor.startMonth`, and only when the caller supplies a non-empty `currentMonthActuals:
CurrentMonthActuals | null` (`{ transactions: ActualTxLike[] }`) as its optional 10th
parameter — booked-only transactions dated within that month, from the account's linked
(non-excluded) cash/savings bank links. The engine itself stays clock-free: callers gate
on "anchor month equals the current calendar month" before passing the param.

**Algorithm** (`src/lib/current-month-actuals.ts`, pure, unit-tested):

- **Phase 1 — exact match**: greedy one-to-one pairing between forecast lines and booked
  transactions, sign-aware (expense↔debit, income↔credit), within amount tolerance
  `max(€1, 5%)` (`ACTUAL_AMOUNT_TOLERANCE_ABS`/`ACTUAL_AMOUNT_TOLERANCE_PCT`). Candidate
  pairs are ranked by name affinity (normalized substring match against the transaction's
  counterparty/remittance-info/transaction-code, with injected `Mortgage:`/`Card:`/`Budget:`
  prefixes stripped from the line name first), then smallest amount delta, then earliest
  `bookingDate`. A matched line contributes `remainingAmount: 0`, `isPaid: true`,
  `matchedTxId`.
- **Phase 2 — category-gap blend**: for expense lines with policy `'full'` that have a
  category and went unmatched in phase 1, unmatched booked debits are categorized via
  `guessItemCategory`; per category, `remaining = max(0, plannedInCategory −
  unmatchedSpendInCategory)`, split proportionally across that category's unmatched lines.
  Uncategorizable debits reduce nothing. Income lines are never gap-blended.
- **Policies** (`ActualMatchPolicy`), assigned per line by `calculateProjection` before
  calling into the module:
  - `'exact-only'` — income lines (any source), `mortgage-payment` lines, and
    statement-basis `credit-card` bills. Never gap-reduced.
  - `'full'` — recurring and planned (one-off/repeating) expense lines. Eligible for both
    phases.
  - `'none'` — `budget` and `goal` lines, and open-cycle/forecast-basis `credit-card`
    bills, left at their planned amount untouched (the open cycle already blends
    actual-vs-forecast spend inside `computeCardBilling`; re-actualizing it here would
    double-adjust it). `trip` lines are income, so they fall under the `'exact-only'`
    income policy above, not this one.
- **Totals semantics**: line items keep `amount` as the planned/effective amount;
  a new `remainingAmount`/`isPaid`/`matchedTxId` on `ProjectionLineItem` carry the
  actualization result. The actualized month's `totalIncome`/`totalExpenses` are the
  **Σ remaining amounts** (so `netChange = totalIncome − totalExpenses` and
  `endingBalance = startingBalance + netChange` still hold, and later months chain from
  the corrected ending balance exactly as before), while `plannedTotalIncome`/
  `plannedTotalExpenses` on `MonthlyProjection` preserve the original planned sums for
  "€X of €Y planned" UI. The row is flagged `isActualized: true`.
- **Pending transactions are excluded** from the transaction set entirely — a bank pending
  row can still change id/amount/counterparty on booking (see [bank-sync.md](bank-sync.md)
  §6, `mergeTransactions`), and the anchor balance itself is booked-first
  (`ANCHOR_BALANCE_PRIORITY` in `src/lib/bank/mappers.ts`), so matching against pendings
  would be matching against data that hasn't settled into the anchor yet.
- **`autoAnchorAccount` is exempt** (`src/lib/bank/sync.ts`): it deliberately never passes
  `currentMonthActuals`. Its bank-sync `BalanceSnapshot.expectedBalance` is meant to
  measure variance against the **pure planned projection**, not an already-actualized one.
- Wiring: `getLinkedCashBankTransactions(userId, accountId)` (`src/lib/projection-inputs.ts`,
  extracted from the retrospective path and shared with it) and
  `getCurrentMonthActualsForAccount(userId, accountId, anchorMonth)` (returns `null` unless
  `anchorMonth` is the current calendar month, or on error/empty data — a bank problem
  never breaks the projection). `gatherProjectionInputs` returns `currentMonthActuals`;
  both `getProjection` and `runScenarioProjection` pass it through to
  `calculateProjection` (see §11).

## 8. Wealth projection (`calculateWealthProjection`)

Input is `WealthProjectionData` (`src/lib/wealth-projection.ts`): cash accounts + their
precomputed `cashProjections` (from `getProjection`), investments + contributions,
receivables + repayments, debts + reference rates + extra payments, per-entity snapshot
maps (`investmentSnapshots`/`receivableSnapshots`/`debtSnapshots`), optional
`mortgageProjections` (+ parallel `mortgageNames`) and `currentUserId`, optional
`cardLiabilities` (`{ linkId, name, outstanding, billYearMonth? }[]`), and optional
`splitNetTotal` (a scalar — positive = owed to the user).

Sub-engines (all anchored via `resolveAnchor`):

- **Investments** (`calculateInvestmentProjection`): monthly growth rate =
  `(1 + annualGrowthRate/100)^(1/12) − 1`; each month adds growth + contributions −
  withdrawals (one-off or recurring `InvestmentContribution`s with the standard interval
  logic).
- **Receivables** (`calculateReceivableProjection`): monthly interest =
  `annualInterestRate/100/12` when `hasInterest`; a month uses the recorded repayments
  if any, else `expectedMonthlyRepayment`; balance floors at 0 and the projection stops
  when repaid.
- **Debts** (`calculateDebtAmortization`): anchor resolved with `negate = true` (debt
  snapshots are stored negative). Rate via `getEffectiveRate`: `none` → 0, `fixed` →
  `fixedInterestRate`, variable → most recent `DebtReferenceRate` at/before the month +
  `referenceRateMargin`. `amortized` debts: `interest = principal × rate/12`,
  `principal = monthlyPayment − interest`. `fixed-installment` debts: pay
  `installmentAmount` while installments remain — the remaining count starts from the
  reconciled `debt.remainingInstallments` when anchored, else `totalInstallments`.
  `DebtExtraPayment`s add principal in their month.

Per month, `WealthProjectionMonth` carries exactly: `cashAccountsTotal`/`Breakdown`,
`investmentsTotal`/`Breakdown`, `receivablesTotal`/`Breakdown` and
`debtsTotal`/`Breakdown` (debt principal positive here; it is subtracted in the sum),
plus the optional `mortgageEquityTotal`, `mortgageLiabilityTotal`, `mortgageStakeTotal`,
`mortgagesBreakdown`, `cardLiabilitiesTotal`, `cardLiabilitiesBreakdown`, and
`netWorth`:

```
netWorth = cash + investments + receivables − debts
         + (mortgageEquityTotal ?? 0)          // guarded: only when data.mortgageProjections && data.currentUserId
         − (cardLiabilitiesTotal ?? 0)          // a card's outstanding drops to 0 at/after its billYearMonth
         + (data.splitNetTotal ?? 0)            // input-side scalar; NOT a WealthProjectionMonth field
```

Mortgage equity is the current member's `equity` (= `stake − liability`) from each
`MortgageProjectionMonth.members` row. The card-liability drop at `billYearMonth`
prevents double counting with the injected cashflow bill line: once the bill month
arrives the cash projection has paid it, so the liability leaves net worth in the same
month. `splitNetTotal` folds in flat (constant across months).

Past-coverage fallbacks (per entity, when the wealth horizon outruns that entity's own
projection rows) all follow the same pattern:

- A **cash account** past its own projection coverage carries forward the **last
  projected `endingBalance`** flat (never the genesis `startingBalance`, which would
  collapse accumulated cash in the tail months); a month before coverage still falls
  back to `startingBalance`.
- A **fully-repaid receivable** contributes 0 for months after its projection rows end
  (`calculateReceivableProjection` stops at balance ≤ 0); only a month before the
  projection starts falls back to `currentBalance`.
- A **paid-off debt** contributes 0 for months after its amortization rows end (not
  `initialPrincipal`).

## 9. Reconciliation

### Data model (`src/types/index.ts`, storage in `src/lib/db/reconciliation.ts`)

- **`BalanceSnapshot`**: `entityType` (`cash-account | investment | receivable |
  debt`), `entityId`, `yearMonth`, `expectedBalance` (system projection),
  `actualBalance` (reported), `variance = actual − expected`, `source?`
  (`'manual' | 'bank-sync'`, default `'manual'`), `createdAt`. **Debt snapshots store
  negative balances** (the wizard negates on write; `resolveAnchor(…, negate: true)`
  converts back).
- **`ReconciliationAdjustment`**: `snapshotId`, `category` (`untracked-income |
  untracked-expense | valuation-change | interest-adjustment | data-correction |
  other`), `amount`, `description?`.
- **`ReconciliationSession`**: `yearMonth`, `status` (`in-progress | completed`),
  `startedAt`, `completedAt?`, embedded `snapshots`/`adjustments` arrays. One session
  per month (re-starting a month reuses its id and keeps its snapshots/adjustments).

All three live in single encrypted files under `data/users/{id}/reconciliation/`
(`balance-snapshots.enc`, `reconciliation-adjustments.enc`,
`reconciliation-sessions.enc`). Cache tag: `user:{id}:reconciliation`.

### `createBalanceSnapshot` — last-write-wins per entity/month

The DB function upserts by `(entityType, entityId, yearMonth)`, keeping the existing id
and replacing everything else (including `source`). So for the **current month**: a bank
sync supersedes an older manual snapshot (the bank is authoritative for a linked
account), and a later manual reconciliation supersedes the bank value until the next
sync. Bank sync only ever writes the current month (`autoAnchorAccount` in
`src/lib/bank/sync.ts`), so historical manual reconciliations are never overwritten.
The sync computes `expectedBalance` by running a baseline `calculateProjection` anchored
on the prior snapshot and reading the current month's `endingBalance`, so bank-sync
snapshots carry a meaningful variance. Bank-sync anchor snapshots are written only for
`cash`/`savings` links with a `linkedFinancialAccountId`; credit-card links feed the
card-liability path instead, not `BalanceSnapshot`s.

### The 3-step wizard (`src/components/reconcile/reconcile-wizard.tsx`)

1. **Month** — pick `yearMonth`; `startReconciliationSession` upserts the session.
2. **Balances** — all non-archived cash accounts, investments, receivables, and debts
   are listed. For cash accounts, `refineExpectedBalances` fetches each account's live
   projection and sets expected = that month's `startingBalance`; actuals are prefilled
   to expected (zero variance until edited). Debts are entered as positive values;
   their variance is computed inverted (`expected − actual`, a decrease is good). Debts
   additionally expose **Remaining Installments** and **Installment Amount** inputs
   (hidden in simple display mode).
3. **Review & complete** — on confirm, for every entity with a non-null actual (changed
   or not — confirming an unchanged balance still moves the anchor):
   - `createBalanceSnapshot` (debt expected/actual negated on write);
   - `applyReconciliationBalances` (`src/lib/actions/reconciliation.ts`) writes the
     actuals into each entity's current-state field: cash `startingBalance`, investment
     `currentValuation`, receivable `currentBalance`, debt
     `initialPrincipal = Math.abs(actual)` plus `remainingInstallments` /
     `installmentAmount` when entered (these current-state updates feed displays and
     genesis fallbacks; forecasts re-base on the snapshot regardless — the account's
     `startingDate` is never touched);
   - `completeReconciliationSession`.

### What a snapshot does to each projection

- **Cash**: forecast re-bases at `{month, actualBalance}`; the retrospective chains
  backward from the same anchor.
- **Investment / receivable**: valuation/balance re-bases at the snapshot month.
- **Debt**: principal re-bases (negated back to positive); when anchored, a
  fixed-installment debt prefers the reconciled `remainingInstallments` over
  `totalInstallments`.

## 10. History compaction

Snapshots, sessions and adjustments accumulate but projections only ever read the
**latest snapshot per entity**, so older history is dead weight, never load-bearing.

`computeCompactionPlan` (`src/lib/maintenance-utils.ts`, pure) returns a
`CompactionPlan`:

- **keep** the latest snapshot per `(entityType, entityId)` (`keptAnchorIds`);
- **prune** all older snapshots, adjustments whose `snapshotId` points at a pruned
  snapshot, and sessions with `yearMonth` strictly before the latest reconciliation
  month across all entities.

Because the plan is anchor-gated it is idempotent (running twice removes nothing new)
and every projection is identical before and after — asserted in
`src/lib/maintenance-utils.test.ts` ("the projection anchor is identical before and
after compaction"). Mortgage data (actuals, drift snapshots — the mortgage engine needs
them from genesis) lives in the shared mortgage storage and is entirely outside this
plan.

Actions (`src/lib/actions/maintenance.ts`): `previewHistoryCompaction` reports counts
without deleting; `compactHistory` deletes (adjustments first, so none dangle
mid-operation) and invalidates `user:{id}:reconciliation`. UI: **Settings → Data &
storage** (`src/app/(dashboard)/settings/page.tsx`).

## 11. Scenarios / "What If?" (`runScenarioProjection`)

`src/lib/actions/scenario.ts`. Ephemeral by construction: no stored entity, no cache
tag; the result lives only in the response.

Mechanics: gather the same inputs as `getProjection` via the shared
`gatherProjectionInputs` (`src/lib/projection-inputs.ts` — account, items, taxed
incomes, anchor snapshot, mortgage/budget/goal/trip transfers, card-filtered lists,
`currentMonthActuals`); run `calculateProjection` for `current` with all transfer
injections; apply the modifications to the **unfiltered** lists (pure logic:
`applyScenarioModifications` in `src/lib/scenario-utils.ts`), recompute the
card-bill transfers from the modified lists, re-apply the `paidByCardLinkId`
filter, and run again for `modified`; return `ScenarioResult`:

```ts
{ current, modified, summary: { currentEndBalance, modifiedEndBalance, difference, monthsProjected } }
```

Modification types (Zod-validated, an array):

- `add-income` / `add-expense` — a synthetic monthly-by-default `RecurringItem` with a
  throwaway id `scenario-${Date.now()}-${Math.random()}` starting the current month, so
  it can never collide with real data. With `isOneOff: true` (+ optional
  `scheduledDate: 'YYYY-MM'`, defaulting to the current month) the modification instead
  appends a synthetic one-off `PlannedItem` (same `scenario-…` id scheme) at that
  month — the Playground's "Once" frequency;
- `remove-item` — filters the item id out of **both** recurring and planned lists;
- `modify-amount` — replaces `amount` on the matching recurring **or** planned item.

Both runs share the same anchor (`latestSnapshot`), taxed incomes, occurrence
overrides, and mortgage/budget/goal/trip transfer injections, and both apply the
`paidByCardLinkId` exclusion — so scenario absolute balances match the cashflow
page. Card-bill lines are recomputed from the **modified** item lists for the
modified run, so modifying or removing a card-tagged expense correctly flows
into (or out of) that card's bill. The same `currentMonthActuals` (§7) is passed
to **both** runs, so a bank-linked account's anchor month is actualized
identically in `current` and `modified` — the modified run re-matches
transactions against its own (possibly modified) lines automatically, since
`applyCurrentMonthActuals` re-runs inside `calculateProjection` for each call.

## 12. Invariants & footguns

- **Never count money twice.** A shared mortgage must not also exist as a `Debt`; a
  linked credit card must not also exist as a `Debt`; the split net balance replaces any
  manual Splitwise receivable; an expense tagged `paidByCardLinkId` must stay excluded
  from direct cash (it lives inside the card bill).
- **Taxed income uses `netAmount`**, never `grossAmount`. Salary reaches the projection
  only as a linked recurring item whose amount is `calculateNetSalary` output.
- **Override flags must survive every write path.** Dropping
  `isRecurringOverride`/`linkedRecurringItemId`/`skipOccurrence` in the DB layer turns
  an override back into a regular one-off → the month double-counts.
- **Debt snapshots are stored negative.** Anything reading them for a debt engine must
  pass `negate: true` to `resolveAnchor` (or `Math.abs`); anything writing them must
  negate first.
- **"Latest snapshot" = greatest `yearMonth`**, not newest `createdAt`. Reconciling an
  old month behind an existing newer snapshot does not move the anchor.
- **Snapshot upsert is last-write-wins per entity/month** — nothing in
  `db/reconciliation.ts` privileges `manual` over `bank-sync`; ordering in time decides.
- **Transfers bypass filters.** Injected mortgage/budget/card lines ignore
  `ProjectionFilters`; only real items are filtered.
- **`filters.startDate` skips flows, not just rows** — balances under a start filter
  begin at the anchor balance regardless of the skipped months' net changes.
- **Injection helpers must never throw.** Each returns `[]` on failure; keep that
  contract when adding a new transfer type, or one broken integration kills the whole
  cashflow page.
- **The retrospective stops at a gap month** and ignores anything at/after the anchor;
  its newest month's `endingBalance` must equal `anchor.startBalance` by construction —
  if those diverge, the anchor and the transaction set were resolved inconsistently.
- **Current-month actualization only applies at the anchor month, and only with
  booked transactions.** `currentMonthActuals` must be `null`/omitted for every other
  month and for accounts with no linked bank data; passing pendings into it would match
  against transactions that can still change id/amount on booking.
- **`autoAnchorAccount` must never receive `currentMonthActuals`.** Its snapshot
  `expectedBalance` measures the plan-vs-reality variance for the pure planned
  projection — actualizing the baseline it's compared against would hide the very drift
  it's meant to surface.
- **Scenario runs must share one `currentMonthActuals`.** Passing it to only one of
  `current`/`modified` (or a stale copy across the two calls) would make the Playground's
  absolute balances diverge from what the cashflow page shows for the same month.
- **Compaction must stay anchor-gated.** Pruning anything other than
  non-latest-per-entity snapshots (or touching mortgage data) breaks the
  byte-identical-projection guarantee.
- **`cleanupExpiredOverrides` must use the anchor-based cutoff** (`anchor − 2` months),
  the same window `calculateProjection` uses — a calendar-based cutoff could delete an
  override a stale-anchored projection still reads.
